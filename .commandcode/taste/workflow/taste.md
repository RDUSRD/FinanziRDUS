# workflow
- Apply edits to the same file sequentially (one edit_file at a time), never as parallel tool calls, to avoid parallel writes clobbering each other's changes. Confidence: 0.65
- Orchestrate implementation/fix tasks with agents rather than doing changes directly (project uses an explicit multi-agent owner contract in docs/architecture.md); he names this himself and repeats it, e.g. asking to fix a layout bug "arreglalo orquestando" and later to dispatch the specialist agent for a whole spec ("orquesta el agente de frontend para hacer lo necesario ..."). Expect an explicit owner boundary: the named agent writes only its own tree (frontend/**) while the orchestrator handles the frozen files outside it. Confidence: 0.85
- When running impeccable design-direction rounds, the user answers through the chat's structured question tool, NOT the served `impeccable serve-question` decision page (the page sat unanswered twice; the tool answer came immediately). Present decision choices via the chat question tool. Confidence: 0.65
- Impeccable 4.3.1 runs through the binary engine at `~/.agents/skills/impeccable/scripts/impeccable` (verbs: context, concept-seed, serve-question, surface-brief, detect). This environment has no image generation (IMAGE_TOOLS empty, no API key), so rounds are code-led: no comps, no `buildPath` toggle; the direction contract lives in the surface brief (never in delivered HTML/comments). When he asks for a visual/structural UI change he green-lights the skill himself ("puedes usar impeccable") and expects the whole cycle run end-to-end on his behalf: activate the skill, explore the real code first, ask the direction questions, lock a composition, write the surface brief, implement, run the finish review and update the design docs — without being told each step. Confidence: 0.70
- When offered, he delegates artifact creation rather than writing it himself: he answers an offer with "puedes crearme entonces el iac de aquí?" and expects the real files produced in the repo (plus the root `package.json`/dependency they need to run), not just a recipe to follow. Confidence: 0.6
- Be economical with tool-call volume per minute: bursts of many quick shell/tool calls trigger cmd's rate limiting which blocks the whole session. Batch related commands into single calls and prefer focused, few tool uses over rapid-fire probes. Confidence: 0.82
- Prefers minimal configuration footprint: when offered extra automation (a Windows logon task to auto-start WSL, enabling linger) versus leaving things manual, he picks the manual/no-extra-changes option and only wants the residual step spelled out. Don't add persistence machinery unasked. Confidence: 0.55
- When a fix could interrupt the currently running agent session, he still prefers to apply the correct/supported fix immediately and verify it now rather than defer it to the next boot: offered "prepare it for next start" vs "apply it now with the CLI", he chose to apply now, trusting that Herdr restores workspaces and that the session can be resumed. Confidence: 0.5
- For a fresh test of the app he wants a genuinely clean-slate state, not demo content: asked to wipe the database and chose the "empty for real" option (drop the data volume, schema + fixed catalogs only, no seed data) over re-seeding the sample data or doing a factory reinstall with the example loaded. Confidence: 0.5
- Sometimes he switches deliberately into a learn-by-doing mode and wants to drive the CLI himself while the agent only instructs: he says so plainly ("Quiero practicar yo los comandos por cli, tu solo dime que ir haciendo"), so stop executing and hand him an ordered, copy-pasteable list of commands — one step at a time, telling him what to look for in each output and what to do if it fails — rather than running them yourself. Confidence: 0.65
- Treats every command block he receives as copy-pasteable verbatim: he ran `D=https://tu-dominio.up.railway.app` (a placeholder) literally and hit Railway's "Application not found". Never leave placeholder values (domains, names, paths) in commands handed to him — substitute the real value you already know, or read it out of the tooling first. Confidence: 0.5
- For disruptive/risky system changes (restarting services, session-killing setups) he may first ask for the exact command to run himself ("dame el comando y yo lo hago") — so deliver a copy-pasteable command with any required env-var workarounds plus verification steps. But he is equally happy to have the agent just execute it: right after seeing it he said "correlo tu entonces" and let the agent run it, and when a step he'd run himself broke the deploy he handed the whole diagnose-and-fix cycle back to the agent ("usa el mcp y revisa y arregla el deploy"), expecting it to use the available tooling (MCP + CLI), patch the config and get the services healthy without further prompting. His drive-it-yourself stance is situational, not fixed: present the command, then be ready to run it — or take over the fix — on request. Confidence: 0.72
- For changes that span backend + frontend, he's comfortable splitting the work across orchestrators rather than doing both stacks in one pass: he asked to "mejorar el backend para dar instrucciones a un orquestador de frontend" — implement the backend now and produce a self-contained handoff/spec document for a separate frontend orchestrator to execute later. He then keeps that document as the working contract: he comes back with it ("De acuerdo a este plan, orquesta el agente de frontend para hacer lo necesario docs/handoff-....md") and expects the orchestrator to read the doc in full and execute its numbered sections by dispatching the specialist agent, verifying the doc's stated premises first and honoring its hard-limit/ownership sections instead of improvising. Confidence: 0.65
- Treat a flaky test as a defect to fix, never as tolerated noise: "Eso hay que resolverlo, no dejarlo." Fix the cause, and prefer an explicit per-test timeout with a one-line comment naming the reason over raising the project-wide `testTimeout` (a global bump would hide genuinely hung tests). Acceptance for a stability fix is three consecutive full-suite runs, all green, with no test sitting close to its budget; report the per-test durations as the evidence. The same repeatability standard applies to the integration smoke test: it must not poison its own state across runs (a login-throttle counter accumulated between runs made it self-block), and the closing evidence is three consecutive green passes. Confidence: 0.6
- Verify rendered UI with evidence that is independent of vision, not with a screenshot read or the stylesheet. A computed style saying an element is painted is not proof it paints; prove contribution by A/B capturing the page with the element present and with it forced off (`display: none`), then diffing a measured metric (e.g. ink-pixel count inside the element's box) so the numbers, not adjectives, decide. Be ready to discard a working hypothesis (including your own capture method) the moment the measurements contradict it. Confidence: 0.6
- After verifying against the live app/API, delete the test records you created so the user's real data is left intact ("Los datos de prueba están borrados (queda sólo tu movimiento 'Huevos')"). Clean up scratch data as part of closing the task. For destructive/contract verification, prefer an entirely isolated stack (its own compose project name, env-file, ports and volume) over his live dev stack, tear it down afterwards, and recreate his stack if the change left it broken — reporting what was touched. Confidence: 0.5
- When a delegated subagent is interrupted or does not report back, inspect the actual repo state yourself (e.g. `git diff --stat` plus grepping the relevant files) to determine which parts actually shipped, then finish the remaining work directly instead of trusting an unfinished/absent report or redoing everything. Confidence: 0.5
- When a frozen API contract forbids something that to him is normal product behavior, he expects the rule to be lifted (and the contract docs updated) rather than the UI to enforce it — he rejects "the contract says so" as the answer and asks for the capability itself. Confidence: 0.55
- Wants new behavior to go through the mechanism/convention he already uses rather than a parallel new rule ("de acuerdo a la tasa usada, como siempre venimos haciendo"): route the new case through the existing helper and reuse its semantics (e.g. convert the total once with the same function that already converts the no-lines case, instead of per-item arithmetic that drifts). Confidence: 0.5
- Expects external research to continue past the repo boundary: when an unfamiliar name/URL/service isn't in the codebase he directs the agent to look it up online ("no existe en el repositorio, buscalo en internet") and wants the answer grounded in the real source (fetch the actual site/docs) rather than an explanation of what it probably is. Reach for web search + fetch before concluding something is unknown. Confidence: 0.5
- Once a personal tool is publicly reachable he wants real authentication, not "no login by design": credentials, opaque tokens with lifetimes, and managed sessions — plus an admin section INSIDE the app to administer those (password, active sessions, block/security policy) rather than relying on host/proxy-level protection. Deliver the security basics as first-class product features, and expect the whole design round (explore the real stack, settle the open decisions, then propose the plan) to happen before any code is written. Confidence: 0.5
- Uses a terse "continua" to tell the agent to carry on — resume after a delegated subagent was interrupted, or move past a step he declined (a disruptive command) — without re-asking for confirmation or waiting on an answer. Confidence: 0.55
- His shell exports the project's env vars (the `set -a; source .env` pattern): `APP_ENV=production`, `NODE_ENV=production`, `SEED_ON_START=false`, `API_PORT`, … live in the ambient environment and leak into every child process. They break the test tooling (`vitest` throws `React.act is not a function` unless run with `NODE_ENV=test`), trip fail-closed config validators (production + the dev `SECRET_KEY` aborts the app before any test runs) and override `docker compose --env-file`. Make suites hermetic — have the suite set its own env before importing the app — and pass the required overrides explicitly instead of assuming a clean shell; tell him the working invocation when the default one fails. Confidence: 0.55
