# communication
- Respond to the user in Spanish; all user messages are in Spanish and the assistant should reply in Spanish. He will explicitly correct a reply that drifts out of Spanish ("Dimelo en spanish"), so never switch languages mid-conversation. His requests are terse and informal, often with typos/abbreviations ("para verlo desde el tlf", "como puedo prender el destokp nodo"), and he expects a short, concrete, action-oriented answer rather than a long lecture. Confidence: 0.9
- Beyond just getting things fixed, he explicitly wants to understand the machinery: he opens with "quiero que me expliques cómo hacer…" and expects a conceptual walkthrough of how the system works (the data-flow through the layers) plus a copy-pasteable command reference grouped by layer, and a triage section for when things fail by symptom. He'll still accept an offer to have it applied for him afterward (he bundles both in one ask: e.g. resetting the DB "para poder probar la app", "y quiero que me digas tambien como funciona"). He also asks the mechanism questions standalone, after the work is already done, purely to understand it ("como funciona la conexion del frontend en la red interna de railway? o como se logra") — answer with the layer-by-layer data flow (browser → edge → nginx → private DNS → service port) even when no action is pending. The same ask extends to tooling he has not met yet: for an unfamiliar third-party AI service he asked only to investigate how to use it with cmd "y como todo se manejaria" — i.e. a layered integration path (binary/CLI + skill → MCP tools → hooks) together with how the thing is administered day to day (listing/enabling/disabling, where the config and keys live, diagnostics, per-call cost). Confidence: 0.85
- When a concept is abstract he wants it re-explained in plain, jargon-free language with everyday analogies, not the dense technical write-up: after a formal IaC walkthrough he asked "explícame de forma que sea más fácil de entender cómo funciona el iac" and got a metaphor-led version (a photo of the desired state, imperative vs. declarative, a Terraform-like cycle). Lead with the plain-language idea/analogy before the mechanics, and drop the jargon. Confidence: 0.5
- Reports failures by pasting the raw terminal transcript (shell prompt, the command he ran, the full error output) with no prose explanation, expecting the agent to diagnose the cause from the output itself — e.g. pasting `railway link` + `railway config pull` → "error: unrecognized subcommand 'config'", or pasting a `tail -f ~/.config/herdr/herdr-client.log` with the repeated `WARN herdr::sound: ... no mp3-capable audio player available` lines. He also pastes production/server logs the same way — e.g. a block of nginx error-log lines from the live Railway deploy — accompanied only by a terse directive ("revisa el railway"), expecting the agent to investigate the platform itself. Read the pasted output for the real cause (stale CLI version, wrong install prefix, missing binary, a stale upstream address) and answer with the diagnosis and the fixing command rather than asking him to clarify. Confidence: 0.65
- He often arrives after already having tried to configure the tool himself through its own menus/UI ("ya lo ajuste de los menus, pero no funciona como deberia"): treat those self-made settings as unverified intent, not as the real state — inspect the actual config files, logs and runtime (binary paths, D-Bus/daemon presence) and diagnose where the described setup silently fails, instead of trusting the described settings. Confidence: 0.5
